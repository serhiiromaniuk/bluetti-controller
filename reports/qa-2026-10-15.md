# Bluetti controller — live UI QA report

**Reviewed:** 2026-10-15 · **Target:** `http://localhost:8080/` · **Role:** experience QA, embedded/mission-critical monitoring · **Scope:** read-only review of the live status and telemetry pages plus their local implementation.

## Review priorities

1. **Stability and data trust (P1):** show whether data is current and whether measurements/estimates are verified; missing data must never look like zero consumption or a healthy battery.
2. **Usability during an outage (P1):** put house grid state and all stations' charge, load, and credible runtime in one glance, with warnings that are hard to miss.
3. **UI self-power and overhead (P2):** reduce browser work, network requests, and server queries when they do not improve the first two priorities. Keep the page local, offline-capable, and quiet when hidden.

## Overall assessment

The app already has the right foundation for a low-resource, outage-ready monitor: server-rendered pages, system fonts, a small vendored chart library, no external page assets, and a telemetry page that renders without JavaScript. The current status page is information-rich, but it asks a user to interpret readings whose trust is explicitly unresolved. The strongest next improvements are honest data states, a compact all-station overview, and event updates that do not reload and rebuild every chart.

**QA disposition: useful MVP, but do not treat unverified SOC, power, or runtime figures as operationally authoritative yet.** This is a UI/data-trust finding, not an independent validation of the device protocol.

## Findings

### P1 — Unverified readings look like decision-grade status

**Evidence:** In the live snapshot, all three cards show `100%` with green battery meters and two show runtime forecasts, while each card is labeled `unverified`. `/telemetry` marks every displayed metric for all three stations unverified. The router card reports `Out 0 W`; telemetry simultaneously reports `ac_output_on = 1` and `ac_output_power = 0 W`. The repo's prior EB3A observation records an outlet powering the router at about 9 W while that power register remained zero (ROADMAP §4.3 / CF-4).

**Why it matters:** A small badge and hover title do not counterbalance large green battery indicators or a numeric runtime. Zero output can also be mistaken for a real zero load. During an outage, that combination can imply more certainty and runtime than the evidence supports.

**Priority / recommendation:** Keep this P1 until each metric has a hardware verification record. Put an explicit, persistent warning beside the station summary and mark affected values/forecasts as provisional. Suppress a runtime forecast when its load source is unverified or implausibly zero while an output is on; show “estimate unavailable — load reading unverified” instead. Preserve raw values on Telemetry for diagnosis.

**References:** [status template](../templates/status.html#L7), [telemetry template](../templates/telemetry.html#L4), ROADMAP §4.3.

### P1 — No visible live/stale state if updates stop

**Evidence:** The status page shows a fixed “Last seen” timestamp and health badge. JavaScript reloads the whole document when an SSE `sample`, `grid_event`, or `poll_failure` arrives, but the page does not display SSE connection state or age readings while it remains open.

**Why it matters:** If the stream drops after the page renders, a user can continue seeing the last green/healthy state without an explicit “stale” banner. The timestamp helps only if the user notices and interprets it.

**Priority / recommendation:** Add a persistent “Updated at …” / “Live” state that changes to a high-contrast “STALE — last sample … ago” after the configured three-poll threshold. Expose stream disconnect/reconnect state and show it independently from station health. Ensure an outage or stale state is announced in text, not by color alone.

**Reference:** [status template](../templates/status.html#L11).

### P2 — Important station information is below the first screen

**Evidence:** At the reviewed 912 px browser width, cards render in two columns; the third station starts below the fold. Each card places a 220 px chart directly under the summary, before the next station card. Outages and energy tables are farther down the page.

**Why it matters:** A person checking backup power needs the state of all three stations before interpreting detailed history. The current layout makes that a scroll task and spends the most visible space on charts.

**Priority / recommendation:** Add a compact overview row near the house grid banner with all three stations' SOC, present load, freshness/trust, and runtime status. Keep detailed charts and history below it or collapsed on small screens. Retain the station cards for drill-down and avoid adding decorative motion.

**References:** [status template](../templates/status.html#L4), [responsive layout](../assets/app.css#L1).

### P2 — Days with no samples appear as real zero-energy days

**Evidence:** The live 7-day energy table shows `0` energy and outage values for prior dates, with `0 s` missing coverage. The implementation computes totals for each day even when `samples` is empty; the history module explicitly documents that a day without samples currently reports `missing_s = 0` and says to count those days if the table misleads in practice.

**Why it matters:** Zero usage and no observations are different facts. A flat zero row can make a gap in monitoring look like a day with verified zero consumption or no outage.

**Priority / recommendation:** Render an explicit “No data” state when there are no samples for a station/day. Keep “0 Wh” only for a measured zero; calculate coverage for a day that never had samples or where collection stopped early. Apply the same distinction to daily house outage totals.

**References:** [energy table](../templates/status.html#L24), [history aggregation and documented caveat](../src/web/history.rs#L69).

### P2 — Each live sample causes a full reload and 15 chart requests

**Evidence:** On every relevant SSE event, the front end schedules `location.reload()` after 2 seconds. Each status page load initializes five metric-series fetches for every station (3 × 5 = 15 requests) and constructs three charts. The project polls every 60 seconds. If an open status page receives one sample group each minute, that is approximately 21,600 chart API requests/day, plus 1,440 page reloads/day. This is a request-count estimate from the code and configured cadence, not a measured energy figure.

**Why it matters:** Re-downloading and re-rendering unchanged history increases browser CPU/network activity and local server/database work. The charts are helpful for diagnosis, but this repeated cost does not improve the glanceable status.

**Priority / recommendation:** Replace full reloads with targeted summary updates. Fetch chart data only when a chart is visible or opened, and return the five metrics for a station in one response (or one compact dashboard series response). Stop or suspend the live stream while the tab is hidden, then refresh once when it becomes visible. Preserve updates for grid changes, failures, and stale warnings.

**Evidence / limits:** `assets/app.js` loads all five series per card and reloads on SSE events. Asset sizes in this checkout are 51,081 B for uPlot JS, 4,203 B for app JS, and 4,118 B combined CSS. Transfer compression/cache behavior, CPU time, and electrical draw were not measured.

**Reference:** [chart fetch and event reload logic](../assets/app.js#L54).

## What is working well

- House grid state is the first visible element; station cards show charge, input/output, forecast, last-seen time, failures, and encryption state.
- The pause control has a bounded 0–60 minute input and communicates its effect; it was not activated during this review because it would interrupt live polling.
- The telemetry page states its verification rule and shows per-metric timestamps and flags.
- The UI uses local assets and system fonts. The telemetry page is server-rendered SVG/HTML and includes no script; it remains light and usable without JavaScript.
- Layout CSS switches to one column below 600 px. A narrow/mobile browser viewport was not exercised in this pass.

## Power and stability measurement limits

This review assessed avoidable work in the UI code and inspected one live desktop rendering. It did not measure host watts, browser energy, CPU time, or network bytes over time; those require a controlled before/after run on the target homelab host. It did not exercise BLE reconnects, stream loss, browser sleep/wake, keyboard-only navigation, or the pause action. Existing automated test results were not rerun as part of this read-only QA pass.

For a useful follow-up measurement, record a baseline and candidate run with the same host, stations, one-minute polling, and browser state: host idle and process watts, app CPU over a fixed interval, HTTP request count/bytes with the status tab visible and hidden, and freshness/recovery after disconnect. Do not trade away the P1 freshness and warning behavior to reduce update frequency.

## Recommended order

1. **P1 — Data trust:** gate or visibly qualify unverified readings and forecasts; handle zero load with output enabled.
2. **P1 — Staleness:** show the data and stream freshness state continuously.
3. **P2 — First-glance usability:** add all-station summary above charts; keep chart detail secondary.
4. **P2 — Honest history:** distinguish no samples from true zeros and report coverage.
5. **P2 — Low-power UI:** replace reloads and 15 chart requests with targeted/batched updates and lazy charts; measure on the target host before and after.

## Risks / Dependencies
- **Order vs the suggested one.** llvm-cov (step 4) moves before the transport work, so every later `make check` already enforces the ≥ 80% protocol threshold instead of finding a gap at the end. `scan` (11) moves before the fixture (12): it tells us whether the EB3A is plaintext before we record anything.
- **Parallel group A (steps 2, 3)** writes disjoint files (`src/config.rs`, `config.example.toml` and the `lib.rs` mod line, vs `src/protocol/modbus.rs`), and neither consumes the other's output. Step 2 edits the existing `lib.rs`, so it gets its own worktree (AGENTS.md §8a). The shared `loop/STATE.md` CF-3 row is the driver's edit after the group. Nothing else is tagged: steps 4 and 8–13 change host tooling or touch the stations, and steps 5–7 each add `mod` lines to `transport/mod.rs`.
- **Adapter split (steps 8, 9):** the bluer code is proven on hardware in the step that writes it — discovery + `scan` in 8, connect/GATT + `detect` in 9 — so a defect surfaces where it was made. Read-only hardware runs are allowed unattended (STATE.md 2026-10-13), which moves the Q4 dependency to step 8.
- **The EB3A may advertise encrypted** (spec §4.5: "absence unverified"). Step 11 finds out first; see the escape hatch.
- **§14 Q5 can be answered only partially** while the AC180 is off. Q3 decides whether a 2-of-3 scan meets the BRIEF; the default is CF-4 → phase 3, where the AC180 is in scope anyway. The Elite's firmware may need the app value (Q2) if it is encrypted.
- **Internal laptop BT combo chip** (spec §4.6: HCI 0x3e aborts) may push the run below 19/20. Mitigations: bounded retries inside one poll (steps 6 and 9), connect-read-disconnect, and app force-quit. A USB dongle is a human host change.
- **bluer #167/#182** (refused connections, hanging `write()`): every op runs under a timeout in step 9. A killed run can leave a stale link: `bluetoothctl disconnect` is local and reversible; `remove` or an adapter reset goes to the human (runbook spec §10.5).
- **Secrets leak via logs:** advertised names carry the SN and scan output carries MACs. LOG pastes always go through `--anonymise`, raw captures stay in gitignored `captures/`, and step 7's MAC-shape scan refuses a staged real address.
- **Coverage filter:** `cargo llvm-cov` has no per-directory threshold. The jq filter must select `src/protocol/` files explicitly, so new modules can never dilute or hide that number.

## Escape hatches
- If a step fails 3 times: stop, log the blocker, set status: blocked, emit `<<LOOP:BLOCKED>>`.
- If a destructive / secret-touching / irreversible external action is required: stop and hand to a human. That covers pairing, any 0x06/0x10 frame, `control.enabled = true`, writing a MAC/SN/key into a config on the host (Q1), BlueZ settings, `bluetoothctl remove`/adapter reset, and installing system packages or a USB dongle.
- Step 14 always stops with `<<LOOP:BLOCKED>>` until the owner's `human-verified` line exists.
- If the EB3A advertises `BLUETTE`/`BLUETTF` (encrypted): stop with `<<LOOP:BLOCKED>>`. Reading it needs the phase-3 handshake, a scope change the owner decides.
- If a hardware step finds no station (app connected, out of range, outside the Q4 window): log it and retry later. It counts toward the 3-failure hatch.
- Gate failures — coverage < 80% on `src/protocol/`, or the acceptance run < 19/20: `<<LOOP:GATE_FAILED>>`. Fix the work (tests, retries, timeouts), never the threshold. A threshold that measures the wrong thing goes only via the falsified-metric path (AGENTS.md §6).

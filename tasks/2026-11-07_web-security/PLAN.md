# Plan — enclose the web UI and API (login, CSRF/Host, headers, caps)

> Written before work starts. **Do not edit the steps once work begins** —
> append changes under `## Amendments`. One step = one loop increment.

Owner's taste (BRIEF, 2026-11-07): "super simple and effective". So: one
password, one session cookie, one guard layer on the router, no accounts table,
no signing keys, no in-app TLS. Host-level work (firewall, reverse proxy,
certificates, system units, deploy) is human-only and ships here as docs only.
Production (homelab, v1.3.4) is untouched until the owner deploys.

## Questions for the owner

Every question below is a product call with a safe, documented default, so the
standing owner delegation (RULES.md) answers it; all are still read out in one
batch at task open so the owner can override before step 1 freezes the spec.
None is pending; no step is blocked.

- Q1 — Auth form: a login page (password → session cookie) with the existing
  bearer `web.token` kept for scripts, or bearer only (entered once, stored in
  a cookie)? · blocks: none · answer: delegated 2026-11-07 — login page +
  `HttpOnly; SameSite=Strict` session cookie for browsers; `web.token` stays as
  the script path (`curl`, `bluetti-update` never needs it). A bearer-in-cookie
  scheme would store the credential itself in the browser. · settled 2026-11-10 in ADR-011 / spec §8.5
- Q2 — Where the credential lives: an argon2id PHC string in
  `web.password_hash` generated by a new `bluetti-controller hash-password`
  (password read from stdin, never argv), or an environment variable? · blocks:
  none · answer: delegated 2026-11-07 — `config.toml`: it already holds
  secrets (`web.token`, the keys path), one config module (RULES.md), no
  scattered env reads. New crate `argon2` (RustCrypto, MIT/Apache, pure Rust,
  pinned) — the one justified addition; nothing in the tree hashes passwords. · settled 2026-11-10 in ADR-011 / spec §8.5
- Q3 — Session lifetime, restart behaviour and lockout: in-memory sessions
  (re-login after a restart, no key in config), 30 days, random 32-byte id from
  `getrandom`; failed logins: after 5 consecutive failures every attempt answers
  `429` for 60 s (one global counter — single user)? · blocks: none · answer:
  delegated 2026-11-07 — yes. A signed cookie that survives restarts needs a
  key in config and a MAC crate; restarts are rare (releases). Persistent
  sessions are a later slice if the re-login annoys. argon2 verification itself
  (~100 ms, `spawn_blocking`, one at a time) is a second natural throttle. · settled 2026-11-10 in ADR-011 / spec §8.5
- Q4 — TLS: none in-app (HTTP on the LAN), in-app rustls with a self-signed
  cert, or a documented reverse proxy (Caddy / Tailscale Serve)? · blocks: none
  · answer: delegated 2026-11-07 — none in-app; ROADMAP.md §2.3 parks "HTTPS on
  the LAN" and this task reopens only the auth half (BRIEF). The ADR records
  why (Wi-Fi link encryption, phone cert warnings for self-signed, three new
  crates) and `deploy/HOMELAB.md` documents Caddy with its internal CA as the
  path if wanted; the cookie is then not marked `Secure` (listed limitation).
  An owner override adds one step (rustls listener) by amendment. · settled 2026-11-10 in ADR-011 / spec §8.5
- Q5 — Remote access beyond the LAN: docs only (Tailscale / WireGuard), nothing
  in-app? · blocks: none · answer: delegated 2026-11-07 — docs only; internet
  exposure is out of scope (BRIEF). · settled 2026-11-10 in ADR-011 / spec §8.5
- Q6 — May GET pages stay readable without login on loopback, and which routes
  stay public? · blocks: none · answer: delegated 2026-11-07 — auth is on for
  every route whenever `password_hash` is set, loopback included (one rule, no
  per-interface mode). Public: `GET /login`, `POST /login`, `/assets/*`,
  `/healthz` (`bluetti-update` and the runbook poll it with plain `curl`,
  `deploy/HOMELAB.md` by DNS name, so it is also exempt from the Host rule; it
  reveals only the build and a poll age). Without `password_hash` the server
  runs in dev mode: loopback only (Q7), everything open, one `warn!` at start. · settled 2026-11-10 in ADR-011 / spec §8.5
- Q7 — Listen-address rule: fail fast when `web.listen` is not loopback and
  `password_hash` is unset; `control.enabled = true` also requires
  `password_hash`? · blocks: none · answer: delegated 2026-11-07 — yes to both:
  a LAN listener is never open by accident, and R3's UI buttons need a session
  (R3's own rule "token required" stays; both hold). · settled 2026-11-10 in ADR-011 / spec §8.5
- Q8 — Host allow-list rule: accept a `Host` whose host part is an IP literal
  (v4 or bracketed v6) or `localhost` (DNS rebinding needs a DNS name, so these
  cannot come from it), and DNS names only from `web.allowed_hosts` (default
  empty)? · blocks: none · answer: delegated 2026-11-07 — yes: the owner reaches
  the host by IP (`192.168.0.192`), so no config in the common case; a name
  like `ideapad.lan` is one list entry. Port is not compared for the Host rule
  (a proxy may rewrite it); the CSRF rule compares the full origin (step 1 d). · settled 2026-11-10 in ADR-011 / spec §8.5

  "any IP literal" would not do; (e) Host rule (Q8); (f) headers —

  frame-ancestors 'none'; base-uri 'none'; form-action 'self'`,

  → `303 /login?next=<path>`, Host miss → `421`, Origin miss → `403`. `spec §9`:

## Risks / Dependencies

- **A breaking config change for the homelab.** v1.3.4 runs with
  `listen = 0.0.0.0` and (per SECURITY.md) maybe only `web.token`; after step 3
  that config fails fast. Mitigation: the Q7 rule is deliberate (never open by
  accident), the upgrade note (step 10) comes before the deploy,
  `bluetti-update` rolls back on a failed `/healthz`, and the owner deploys
  (human-only). The dev laptop's user unit needs the same edit before a local
  run.
- **R3 ordering** (`2026-11-07_r3-control-schedule`, not edited here). Either
  order works: if R3 lands first, step 6 also removes the per-handler bearer
  check from `src/web/control.rs` and moves its 401 test; if this lands first,
  R3's step 10 adds its routes to the protected router, lists them in
  `PROTECTED` (the route-scan test fails until it does) and skips the bearer
  code. R3 must not be enabled on the homelab before step 6 is deployed (H19);
  R3's Q5 "token required" and this task's Q7 "hash required" both stay.
- **CSRF and same-site ports.** `SameSite=Strict` still sends the cookie to a
  page on the same IP at another port, so the Origin check is an exact-origin
  comparison against the request's own `Host` (step 1 d, step 6), not an
  IP-literal allow; the `:9999` test proves it.
- **Login memory.** argon2id at 19 MiB per verification, serialised by a
  one-permit semaphore and counted before verification, bounds a flood to one
  hash in flight and five verifications per lockout window (step 4/5 test).
- **CSP breaks inline scripts.** `base.html` has two inline `<script>` blocks
  (theme). Step 7 moves them to `assets/theme.js` before the header ships;
  the `grep` check proves none is left. A nonce scheme is rejected (more code,
  no gain).
- **`/healthz` stays public and Host-exempt** by design (Q6): `bluetti-update`
  and `deploy/HOMELAB.md` curl it, the latter by DNS name; it leaks only the
  build string and a poll age.
- **SSE and cookies.** `EventSource` sends same-origin cookies, so `/events`
  needs no special case; verified by the route walk with a cookie (step 6).
- **In-memory sessions** end on restart (Q3) and live in one `Mutex`; the cap
  of 16 bounds memory for the single user. Sessions survive restarts only via
  a later slice (SQLite table through the one writer), not here.
- **One new crate** (`argon2`) — justified in Q2/ADR-011, pinned, MIT/Apache;
  `make check` plus `cargo tree` prove no GPL transitive dependency. Nothing
  else: middleware is `axum::middleware`, randomness is the existing
  `getrandom`, the semaphore is `tokio::sync`, the constant-time compare is
  the existing `same`.
- **File sizes.** `src/config.rs` is near the cap: web validation and its tests
  go to `src/config/web.rs`; auth is `auth/session.rs` (store, lockout),
  `auth/password.rs` (argon2) and `auth/mod.rs` (handlers); the guard and
  headers are their own files.
- **Parallel group A = {8, 9}**: `api.rs`/`history.rs`/`store/read.rs` + their
  tests vs `cli/*` — disjoint files, no shared output; one batched `reviewer`
  pass. Steps 1–7 are a dependency chain (spec → hashing → config → store →
  handlers → guard → headers) and each is risky or edits `web/mod.rs`, so they
  run alone. Risky steps (1–6) are reviewed before their commit; 7–10 in
  batch.
- **Out of scope stays out** (BRIEF): multi-user, roles, OAuth, in-app TLS,
  host firewall/proxy install, limitation 4 (BLE reply binding) and the
  `bluetti-update` items — none is folded in; they stay in "Planned hardening".

## Escape hatches

- If a step fails 3 times: stop, log the blocker, set status: blocked, emit `<<LOOP:BLOCKED>>`.
- If a destructive / secret-touching / irreversible external action is required
  — editing the homelab's `config.toml`, deploying, installing a proxy or
  certificate on a host, a system unit, a firewall rule, writing a real password
  or hash anywhere in the repo — stop and hand to a human (`<<LOOP:BLOCKED>>`).
  Test hashes are of throwaway strings (`"test"`), never an owner password.
- If the gate fails (`make check` red, a done-when line without a green test,
  a route reachable without credentials): `<<LOOP:GATE_FAILED>>` on the third
  attempt — fix the work, never the threshold.
- If the owner overrides Q4 (in-app TLS): an amendment adds one step (rustls
  listener + `Secure` cookie), not a rewrite.
